## 一、系统架构总览

```
用户（浏览器/H5）
   │
   ▼
【gateway 网关】  ← 统一入口：路由转发 / 鉴权 / 限流 / 跨域 / 日志
   │  按路径分流
   ├──▶ user-service  → 注册/登录/我的界面
   ├──▶ product-service → 首页/演出浏览搜索/详情/票价
   ├──▶ seat-service  → 座位图加载 / 锁座 / 释放
   ├──▶ cart-service  → 购物车（非秒杀场次批量结算）
   ├──▶ seckill-service → 免选座秒杀（Redis Lua 扣库存）
   │        └─ 扣中 → 发 Kafka 消息
   ├──▶ order-service  → 消费者落单 / 订单查询 / 退款 / 超时取消
   │        ├─ 支付回调（来自 payment-service）
   │        └─ 回补库存（product/seat）
   └──▶ payment-service(Mock) → 支付对接
```

## 二、微服务划分与职责

| 服务 | 职责 | 备注 |
|---|---|---|
| **gateway** | 路由转发、统一鉴权、全局限流、跨域、日志 | Spring Cloud Gateway + Nacos |
| **user-service** | 用户注册/登录、JWT 双Token、我的界面；**图形验证码(Hutool) + SmsService 抽象(Mock)** | — |
| **product-service** | 演出/场次/票档/座位图 CRUD；首页浏览搜索 | — |
| **seat-service** | 座位图加载、锁座、释放 | 核心：选座一致性 |
| **cart-service** | 购物车（非秒杀场次，批量结算） | 可扩展实例 |
| **seckill-service** | 免选座秒杀抢票（Redis Lua 扣库存、一人一单、Kafka 消息发送） | 核心：秒杀一致性 |
| **order-service** | 订单落库（Kafka 消费者）、订单查询、取消、退款、超时回补 | 核心：状态机 |
| **coupon-service** | 优惠券模板/领取/购买/券包/下单选券（策略模式） | 本期新增 |
| **payment-service** | 支付对接（Mock）、回调 | Seata 局部使用 |
| **notification-service** | `[TBD]` 通知推送 | 演进点，当前简化 |
| **file-service**（或并入 common） | 图片上传/压缩/MinIO | 本期新增 |
| **common** | 雪花 ID、幂等表、锁客户端、Kafka 消息封装、**通用领取引擎** | 公共模块 |

> 服务数量提示：2C4G 上约 10 个 JVM，需低内存调优（每 JVM ~256MB）；若吃紧可把 coupon 并入 order-service、file 并入 common（降级路径）。

## 二·补 通用能力层（复用亮点）

**通用领取引擎（common）**——票与券复用同一套"限量+限购+并发+幂等"机制：

| 能力 | 说明 | 复用方 |
|---|---|---|
| 库存扣减 | Redis Lua 原子扣减（单 key，未分桶） | 票档库存、限量券库存 |
| 用户维度去重/限购 | 一人一单 / 一人限领 N（参数化） | 秒杀票、限量券 |
| 幂等 | 唯一键防重复落库 | 订单、用户券 |
| 异步落单 | 本地消息表 + Kafka + 消费者幂等 | 票单、券单 |

**优惠券策略模式**：`CouponStrategy` 接口（`applicable` / `calculate`），实现 `满减/折扣/立减`，Spring 注入 `Map<type, strategy>` 路由；新增券种不改老代码（开闭原则）。

## 二·补2 状态机总览

| 对象 | 状态 |
|---|---|
| 演出 product | 草稿 / 已上架 / 售罄 / 已结束 |
| 场次 session | 待开票 / 售票中 / 售罄 / 已结束 |
| 订单 order | 待支付 / 已支付 / 已完成 / 已取消 / 已退款 |
| 用户券 user_coupon | 未用 / 锁定 / 已用 / 已释放 / 已过期 |

**超时三释放**（订单超时/取消时）：票档库存回补 + 座位释放 + 券释放，全部按 `order_id` 幂等；由**定时扫单**触发。

## 三·补 核心业务时序（推演结论）

### 时序1：免选座秒杀购票（含用券）
```
① 抢票页 → 展示可用券（strategy.applicable 过滤）
② 点"抢票" → Redis Lua：扣票档库存 + 一人一单校验
③ 抢中 → 锁定所选券（UNUSED→LOCKED）
④ 算价 = 票档价 → strategy.calculate → 落订单（待支付）
⑤ 支付成功 → 券 USED + 已支付；超时/取消 → 三释放
```

### 时序2：选座购票（含用券）
```
① 打开座位图（Redis 优先）
② 点选 → 锁座（Redis CAS + lock_token + TTL短）
③ 结算 → 选券 → 算价
④ 下单 → 待支付 + 券锁定 + 座位"已售(待支付)"
⑤ 支付 → 确认；超时 → 三释放
```

### 时序3：限量券领取（复用通用领取引擎）
```
① 领券 → Redis Lua：扣券库存 + 每用户已领数 < per_user_limit
② 成功 → 本地消息表 → Kafka → 消费者幂等落 user_coupon
```

### 时序4：不限量券购买（一人可购 N）
```
① 券中心 → 选券 → 下单（order_type=COUPON）
② 限购校验：已购 + 本次 ≤ per_user_limit
③ 支付成功 → 发放用户券（幂等）
```

### 时序5：订单超时三释放
```
定时扫单（待支付且超时）→ 取消订单 → 库存回补 + 座位释放 + 券释放（按 order_id 幂等）
```

### 时序6：登录（密码 / 短信验证码）
```
① 请求图形验证码 GET /captcha → 后端 Hutool 生成 → 答案存 Redis(captchaId,TTL5min)，返回图片
② 发送短信 POST /sms/send {phone, captcha_id, captcha_input}
     → 校验图形验证码(一次性，校验后删) → 通过才发短信(Mock: 写Redis+日志) 
③ 登录 POST /login {phone, password} 或 {phone, code}
     → 校验通过 → 签发 Access Token(15min) + Refresh Token(7d)
④ 刷新 POST /refresh；登出 POST /logout(黑名单即时失效)
```
- 抽象 `SmsService`：开发 `MockSmsService`、生产真实 SDK，业务无感。

## 四、部署形态与演进路线

### 阶段0（当前）：本机 Docker Compose

```
TicketGo 全套微服务（gateway + user + product + seat + seckill + cart + order + payment-mock + notification-mock）
MySQL / Redis / Kafka（KRaft）/ Nacos
全部在 2C4G 本机 Docker 内运行
```

- 开发/联调/压测/演示全在本机，不受资源限制
- payment/notification 用 Mock（不接真支付/真短信）
- 内存预算：约 3GB（含 Kafka~350MB + MySQL~450MB + Redis~200MB + JVM×8@256MB + Gateway）

### 阶段1（后续）：搬上 2C4G 云服务器

- 低内存版 Compose，payment/notification 仍用 Mock
- 演示与巡检对象本地/上云一致，上云只改配置不改代码
- 云上形态 A（全服务+Mock）为目标，B（裁剪 4 核心服务）为降级路径

### 阶段2（设计预留，不执行）：集群扩容

| 步骤 | 操作 |
|---|---|
| ① | 加服务器实例（服务无状态，Nginx/Gateway 负载均衡） |
| ② | Redis 单机→主从/Cluster |
| ③ | Kafka 分区提升 + 消费组并行 |
| ④ | MySQL 读写分离 + 分库分表 |

### 为什么能扩（四个面试支点）

1. 服务无状态 + Session 落 Redis + JWT 无状态 → 加实例即吃流量
2. Redis Cluster（库存分桶天然适配）→ 热点 key 不成为瓶颈
3. Kafka 分区 = 并行度 → 加分区不破坏同一订单顺序（按订单号 hash 分区）
4. 分表路由不变前提做读写分离 → 扩容不动业务代码

## 五、核心数据流

### 5.1 抢票主流程

```
用户 → gateway → seckill-service
  → Redis Lua 原子扣库存（校验库存>0 → 扣减 → 记用户已购 → 返回成败）
  → 成功 → 发 Kafka 落单消息
  → 消费者（order-service）落 MySQL（幂等去重）
  → 用户限时支付 → payment-service(Mock) 回调 → order-service 更新状态
  → 超时未支付 → order-service 取消订单 → 回补库存（product/seat）
```

### 5.2 选座购票流程

```
用户 → gateway → seat-service（加载座位图）
  → 选座 → 锁座（Redis CAS + TTL）
  → 加入购物车（非秒杀）/ 直接下单（秒杀）
  → 支付 → 释放锁座 / 超时自动释放
```

## 六、T1b 已定：落单可靠性方案

- **本地消息表 + 定时投递 + 消费者幂等**（Kafka 事务消息/普通消息作对比·演进点）
- 理由：本地事务把"业务表 + 待发消息表"绑一起 → 消息必达不丢
- 消费者按 `order_id` 唯一索引幂等 → 零重单
- 有限重试 → 死信队列 → 人工修复 → 最终可恢复
