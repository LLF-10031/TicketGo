## 一、消息队列选型与 Kafka

### 1.1 Kafka vs RabbitMQ vs RocketMQ

| 维度 | **Kafka** | RabbitMQ | RocketMQ |
|---|---|---|---|
| 模型 | 分布式日志（分区 pull） | AMQP 队列（push） | 类 Kafka（队列） |
| 吞吐 | **极高（百万级）** | 中（万级） | 高（十万级） |
| 延迟 | 较低 | 极低 | 低 |
| 顺序 | 分区内有序 | 队列有序 | 队列有序 |
| 路由 | 简单（topic/分区） | **复杂（exchange 路由）** | 较丰富 |
| 事务消息 | 支持（较重） | 不支持（用确认替代） | **支持（成熟）** |
| 延迟消息 | 需插件/自实现 | 插件（延迟队列） | **原生支持** |
| 场景 | 日志/大数据/高吞吐削峰 | 业务解耦/复杂路由/低延迟 | 电商交易/金融 |

### 1.2 为什么票务抢票选 Kafka？
- **大吞吐削峰**：开票瞬间海量请求，Kafka 百万级吞吐扛得住。
- **分区顺序**：按订单号 hash 分区，保证同一订单的消息有序。
- **持久化 + 可回溯**：消息落盘、可重放，适合订单链路。
- **生态成熟**：KRaft 免 ZooKeeper，运维简化。
- 对比话术：*"RabbitMQ 的强项是复杂路由/低延迟，Kafka 的强项是高吞吐削峰，我们抢票是典型高吞吐场景，所以选 Kafka。"*

### 1.3 Kafka 核心术语
| 术语 | 含义 |
|---|---|
| Broker | 一个 Kafka 服务节点 |
| Topic | 消息主题（逻辑分类，如 `order-created`） |
| Partition | 分区，Topic 的物理分片，**并行度单位** |
| Offset | 消费者在分区内的消费位移 |
| Consumer Group | 消费组，组内一个分区只被一个消费者消费 |
| Replica | 副本（1 leader + N follower），保证高可用 |
| ISR | In-Sync Replicas，与 leader 保持同步的副本集合 |
| acks | 生产者确认级别（0/1/all） |
| Rebalance | 消费组重平衡（分区重新分配） |
| Lag | 消费滞后（积压量） |
| Retention | 消息保留时长/大小 |
| 幂等生产者 | producer id + sequence 去重，防重复写入 |

### 1.4 可靠性三问
- **不丢**：producer `acks=all` + 重试；broker 持久化 + 多副本；consumer 手动提交 offset。本项目另加**本地消息表**保证业务与消息同事务。
- **不重**：消费者幂等（订单唯一键）。
- **不堆积**：分区数预留并行度；消费端批量；死信兜底。

## 二、MySQL 索引与表结构设计

### 2.1 索引基础
- **B+树**：为什么用 B+ 不用 B 树/哈希？——B+ 叶子节点串成链表、范围查询高效、树矮（磁盘 IO 少）；哈希只支持等值。
- **聚簇索引**：主键即数据（InnoDB），叶子存整行。
- **二级索引（非聚簇）**：叶子存主键值，查非索引列需**回表**。
- **最左前缀**：联合索引 `(a,b,c)` 能用 a、a+b、a+b+c，不能只用 b。
- **覆盖索引**：查询列都在索引里 → 免回表。
- **索引下推（ICP）**：在存储引擎层提前过滤，减少回表。
- **Explain**：看 type/key/rows/Extra（Using index = 覆盖索引）。

### 2.2 表结构设计原则
- 字段类型尽量小（能用 INT 不用 BIGINT）；金额用 DECIMAL。
- 合理范式 + 适当反范式（读多写少可冗余）。
- **唯一索引做幂等**（订单号/业务唯一键）。
- 索引选择性高才建（区分度低的不建）。
- 避免 `select *`；避免在索引列上做函数运算（破坏索引）。
- 高频查询走联合索引，注意最左前缀与顺序（等值在前、范围在后）。

### 2.3 本项目索引举例
- `order (order_no)` 唯一：幂等 + 单查。
- `order (user_id, status, create_time DESC)`：查"我的订单"。
- `order (status, pay_expire_at)`：扫超时订单。
- `message_outbox (status, next_retry_at)`：扫待重发消息。

## 三、数据库选型：MySQL vs PostgreSQL

| 维度 | MySQL | PostgreSQL |
|---|---|---|
| 定位 | 轻量、快速、易用 | 功能强、类型丰富、标准兼容 |
| 事务/隔离 | InnoDB MVCC | MVCC（无回滚段，更优） |
| JSON | JSON 支持一般 | **JSONB 强（可索引）** |
| 扩展类型 | 一般 | 数组/范围/几何/自定义类型 |
| 向量 | 需插件 | **pgvector 原生一体** |
| 全文检索 | 一般 | 强（tsvector） |
| 分区 | 支持 | 声明式分区成熟 |
| 生态/运维 | **国内生态最成熟、工具链多（ShardingSphere/MyCat）** | 稍弱但增长快 |
| 适用 | 交易/电商/互联网主库 | 复杂分析/JSON/地理/向量 |

**本项目选型话术**：
- **TicketGo 选 MySQL**：交易类（订单/库存）**生态成熟、分库分表工具链完善（ShardingSphere）、团队熟悉、云支持广**。
- **OpsMind 选 PostgreSQL**：需要 **JSONB 存半结构化 + pgvector 向量检索一体存储**，避免多维护一套向量库；PG 更适合"元数据+向量+记忆"混合场景。
- 面试金句：*"选型看场景——交易选 MySQL（生态与分库分表工具链），AI/向量与 JSON 选 PG（JSONB + pgvector 一体）。"*

## 四、Redis 集群专题（了解即可，本项目未落地）

- **哈希槽**：Redis Cluster 固定 **16384 个 slot**，`slot = CRC16(key) % 16384`，slot 分配给各节点。
- **为什么 16384**：节点数目标（千级）+ 分布均匀 + 位图大小（2KB）便于 gossip 同步。
- **MOVED 重定向**：key 不在当前节点 → 返回 MOVED 指向正确节点，客户端/代理自动跟随。
- **hash tag**：`{xxx}` 内的内容参与 CRC16，可让多 key 强制同 slot → **Cluster 下 Lua/事务的多 key 必须同 slot**。
- **主从 vs 分片 vs 哨兵**：
  - 主从：读写分离/高可用，**写仍在主**。
  - 哨兵 Sentinel：监控 + 自动故障转移（主从的高可用方案）。
  - 分片 Cluster：key 分散到多节点 → **写扩展**；自带高可用。
- **为什么本项目不做**：单机 2C4G 规模下单 key 完全够用；集群/分桶属"面向未来的架构预留"，写进演进路线与面试问答，不落地。
