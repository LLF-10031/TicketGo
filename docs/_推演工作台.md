## 二、逐场景推演明细

### 🅢1 演出/票档上架（含图片上传+压缩）

**正常流程 v1**
```
管理端 → 创建演出(名称/分类/简介) → 上传海报 → 保存URL
       → 创建场次 → 配置票档(价格/库存) → 上架 → 用户可见
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 存原图 | 海报几 MB，列表一次加载几十张 → 慢、费流量、占空间 |
| P2 无校验 | 大文件/非法格式可传 → 打爆存储 |
| P3 无状态 | 配一半的演出就被用户看到 |
| P4 同步压缩 | 大图压缩阻塞上传接口 |

**迭代 v2**
```
上传 → 校验(格式 jpg/png/webp、大小上限、防重命名) 
     → 压缩(等比缩放到最大宽 + 质量压缩) 
     → 生成缩略图(列表用) 
     → 存 MinIO → 返回 URL
演出先存"草稿"，配置完整才"上架"
```
- 多规格：原图(留存) / 展示图(详情) / 缩略图(列表)。
- MinIO bucket 分目录：`poster/`、`avatar/`、`seat-map/`。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 异步压缩 | 小图同步、大图丢异步任务（线程池/@Async），压缩完回填 URL 状态 |
| 参数可配 | 最大宽、质量比放 Nacos |
| 状态机 | 演出：`草稿 → 已上架 → 售罄 → 已结束`；仅"已上架"用户可见 |
| 孤儿图清理 | 未绑定业务的图打标记，定时任务清理 |
| 图片与数据一致 | 先传图得 URL → 再保存演出；删除演出时标记图片待清 |

**收敛设计点**
- 图片链路：校验 → 多规格压缩 → MinIO → URL；列表走缩略图。
- 演出状态机四态。
- 面试话术：*"图片做多规格压缩（原图/展示/缩略）+ 异步压缩，列表走缩略图省带宽；MinIO 对象存储 + Nacos 配参 + 孤儿图清理。"*

### 🅢2 场次/库存/开票时间

**正常流程 v1**
```
管理端 → 创建场次(场馆/演出时间/开票时间/截止时间) 
       → 配置票档(名称/价格/库存) → 保存
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 开票前可下单 | 未到开票时间用户就能抢 → 业务错误 |
| P2 库存仅 DB | 开票瞬间查 DB 扣减 → 打爆且竞态 |
| P3 状态不会自动变 | 到点不自动"售票中"/"已结束" |
| P4 改库存无审计 | 管理端改库存无记录，可能与 Redis 不一致 |

**迭代 v2**
- 场次状态机：`待开票 → 售票中 → 售罄 → 已结束`；用**定时任务**按开票/截止时间自动切换。
- 开票前把票档库存**预热到 Redis**（`stock:{tierId}`）。
- 下单口校验"当前时间在售票窗口内"。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 时间统一 | 服务端统一时间源；开票判定以后端时间为准，前端倒计时仅展示 |
| 预热补偿 | 预热失败/漏做 → 定时补偿任务扫描"售票中但 Redis 无库存"的票档补预热 |
| 改库存审计 | 库存变更留审计记录（谁/何时/改前改后）；改库存时同步刷新 Redis |
| 防超卖 | 实际扣减全在 Redis Lua，DB 仅落账 |

**收敛设计点**
- 场次四态状态机 + 定时切换。
- 开票预热库存 + 补偿任务。
- 库存变更审计 + 同步 Redis。

### 🅢3 座位图配置（选座场次）

**正常流程 v1**
```
管理端 → 选择"选座型"场次 → 上传座位图/定义排×列 → 划分票档区域 → 生成座位
       → 用户端加载座位图 → 点击选座
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 座位无唯一标识 | 并发选座无法判断"谁锁了哪个座" |
| P2 座位与票档脱节 | 不知道某座属于哪个价位 |
| P3 锁座不释放 | 用户选了不买，座位被永久占用 |
| P4 直观性 | 前端要能画出座位图（布局/坐标） |

**迭代 v2**
- 座位表：`session_id, tier_id, row_no, col_no, x, y, status(可售/锁定/已售), lock_token, lock_expire_at`。
- 座位状态：`0 可售 / 1 锁定 / 2 已售`。
- 锁座：`Redis CAS(setnx) + lock_token + TTL`，到期自动可抢。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 分区 | 座位按票档分区（A区/B区），价格与区域绑定 |
| 批量生成 | 按排×列批量生成，支持过道/空位 |
| 锁座与订单解耦 | 锁座超时（短，如5分钟）；订单支付超时（长，如15分钟）各自处理 |
| 座位图数据 | 座位坐标/区域信息存 JSON，前端按坐标渲染 |

**收敛设计点**
- 座位建模（含坐标+票档+状态+锁）。
- Redis 锁座 CAS+TTL，超时自动释放。
- 注意：锁座超时 ≠ 订单超时，两者分开（S8 细讲）。

### 🅢4 优惠券模板上架（管理端）

**正常流程 v1**
```
管理端 → 创建券模板(名称/类型/面额/门槛/适用范围/有效期/总量/每人限购数)
       → 上架 → 用户可领取/购买
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 券种算法写死 | 满减/折扣/立减用 if-else → 加券种要改老代码 |
| P2 限量规则不统一 | "限量1人1份" 与 "不限量1人N份" 混在一起难表达 |
| P3 适用范围模糊 | 不知道券能用在哪场演出/多少钱起 |
| P4 有效期口径 | 固定日期 vs 领取后N天 |

**迭代 v2（策略模式）**
- `CouponStrategy` 接口：`type()` / `applicable(order, coupon)` / `calculate(origin, coupon)`。
- 实现：`FullReduceStrategy`（满减）、`DiscountStrategy`（折扣，可封顶）、`ImmediateStrategy`（立减）。
- Spring 注入 `List<CouponStrategy>` → `Map<type, strategy>` 路由；**新增券种只加类、不改老代码（开闭原则）**。

**迭代 v3（券模板字段定稿）**
| 字段 | 说明 |
|---|---|
| type | 券种：full_reduce / discount / immediate |
| threshold_amount | 使用门槛（满 X） |
| discount_amount / discount_rate / max_discount | 满减面额 / 折扣率 / 折扣封顶 |
| scope_type | 适用范围：全部 / 指定演出 |
| scope_product_ids | 限定演出 ID 列表 |
| valid_type | 有效期：固定区间 / 领取后N天 |
| valid_start / valid_end / valid_days | 对应有效期值 |
| **stock_type** | **限量 / 不限量** |
| total_qty | 总量（限量时有意义） |
| **per_user_limit** | **每人限购数（管理端配置；"限量券"设为1）** |
| acquire_type | 获取方式：领取(免费) / 购买(需支付) |
| price | 购买价（acquire_type=购买时有意义） |
| status | 草稿 / 已上架 / 已结束 |

**收敛设计点**
- 策略模式承载券种算法（扩展不改旧码）。
- **限量类型 + 每人限购数由管理端配置**（限量券=限量+per_user_limit=1；不限量券=不限量+per_user_limit=N）。
- 券模板四态 + 适用范围（金额门槛 + 限定演出）。

### 🅢5 限量券领取（并发抢券）

**正常流程 v1（直觉）**
```
用户 → 点"立即领取" → 查库存 → 有 → 扣1 → 生成用户券
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 并发超发 | 100 张券，同时 500 人查"还有"→ 都扣 → 发出 500 张 |
| P2 一人领多张 | 无用户维度去重 → 同人刷多张 |
| P3 与票秒杀重复实现 | 又要写一套 Lua/幂等/异步 → 重复代码 |

**迭代 v2（复用通用领取引擎）**
- 复用 common 的**通用领取引擎**（与票秒杀同一套）：
  - Redis Lua 原子：`校验券库存 → 扣1 → 记录该用户已领(<=per_user_limit) → 返回成败`
  - 成功后异步落库（本地消息表 + Kafka + 消费者幂等），与 T1b 同链路。
- 限量券：库存>0 且 用户已领数 < per_user_limit 才成功。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 限领计数 | 每用户领券数用 Redis Hash `user_coupon_count:{templateId}` 或 Set 记录 |
| 幂等 | 用户券唯一键 `(user_id, template_id, seq)` 防重复落库 |
| 领取结果通知 | 复用 SSE/WebSocket 告知结果 |
| 不限量券不走此路 | 不限量且需购买 → 走 S6 券订单 |

**收敛设计点（复用亮点）**
- **票和券共用"通用领取引擎"**：库存扣减 + 用户维度去重 + 幂等 + 异步落单，参数不同（是否限量、限购数）。
- 面试话术：*"票和券的限量+限购+并发+幂等是同一类问题，我抽了通用领取引擎，两者复用，避免两份一致性逻辑各自出 bug。"*

### 🅢6 不限量券购买（一人可购 N，N 由管理端配）

**正常流程 v1**
```
用户 → 券中心 → 选券 → 购买 → 支付 → 获得用户券
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 券也是"商品" | 券购买需要订单+支付 → 与票订单是否共用？ |
| P2 限购 | 每人可购 N，N 由券模板 `per_user_limit` 配置 |
| P3 券落库时机 | 支付成功才发券，还是下单就发？ |

**迭代 v2（券订单独立）**
- 订单增加 `order_type`：`TICKET`（票订单）/ `COUPON`（券订单）/ `MEMBER`(预留)。
- 券订单金额 = 券单价 × 数量；走同一支付链路（payment-service）。
- **支付成功后才发放用户券**（避免未付款拿券）。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 限购校验 | 下单时校验"已购数 + 本次数量 <= per_user_limit"；并发用 Redis 计数或 DB 唯一约束 |
| 券订单与票订单分表/分类型 | 同表 `order_type` 区分，便于统一状态机；金额/明细走各自 item |
| 发放幂等 | 支付回调消费幂等，按 `order_id` 只发一次券 |
| 与秒杀区分 | 券购买是普通下单（非秒杀），无需 Lua 扣库存（不限量）；限量券可购买则复用 S5 |

**收敛设计点**
- 订单表加 `order_type` 区分票单/券单，共用状态机与支付链路。
- 券购买支持"每人限购 N"（来自模板配置）。
- 支付成功发券 + 幂等。

### 🅢7 免选座秒杀购票 + 用券

**正常流程 v1**
```
用户 → 开票瞬间 → 点抢票 → 扣 Redis 库存 → 下单 → 支付 → 完成
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 券何时用 | 抢票时选券？还是下单时？ |
| P2 券锁定与库存 | 券锁了但票没抢到 → 券要释放；票抢到券锁失败 → 怎么算 |
| P3 超时释放 | 库存/券都要释放 |
| P4 算价顺序 | 秒杀价 vs 券抵扣的顺序 |

**迭代 v2（时序定稿）**
```
① 用户进入抢票页 → 展示可用券列表（strategy.applicable 过滤）
② 点"抢票"（可预先选券）→ Redis Lua 扣票库存 + 用户去重（一人一单）
③ 抢中 → 锁定所选券（user_coupon: UNUSED→LOCKED，绑订单）
④ 计算金额 = 票档价 → strategy.calculate（券抵扣）→ 落订单（待支付）
⑤ 支付成功 → 券 USED + 订单已支付；超时/取消 → 库存回补 + 券释放
```

**迭代 v3（边界处理）**
| 边界 | 处理 |
|---|---|
| 抢到票但券锁定失败 | 抢票时不硬绑券：**下单前再校验券**；券不可用则按原价下单或提示重选（二选一，取"提示重选"更严谨） |
| 券抵扣后金额为0 | 允许 0 元订单，直接置"已支付"，跳过支付（可选规则） |
| 抢票成功但未支付 | 超时取消 → 库存回补 + 券释放（S9 三释放） |
| 一人一单 + 用券 | 一人一单是票维度；券是另一维度，互不干扰 |

**收敛设计点**
- 秒杀用券时序：抢票扣库存 → 锁券 → 算价 → 落单。
- 超时走三释放（S9）。
- 面试话术：*"券在下单前校验并锁定，抵扣用策略模式算价；抢到未付超时会同时回补库存并释放券。"*

### 🅢8 选座购票 + 用券

**正常流程 v1**
```
用户 → 打开座位图 → 点选座位 → 下单 → 支付 → 完成
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 同座并发 | 两人同时点同一座 → 都下单？ |
| P2 锁座超时 vs 订单超时 | 两个时间口径不同 |
| P3 券与座位 | 选券在锁座前还是后 |
| P4 座位释放 | 未支付 → 座位要放回 |

**迭代 v2（时序定稿）**
```
① 打开座位图 → 读座位状态（Redis 优先，DB 兜底）
② 点选 → 锁座：Redis Lua/CAS 原子占座 + lock_token + 座位锁 TTL(如5分钟)
③ 结算页 → 选券（applicable 过滤）→ 算价
④ 提交订单 → 生成订单（待支付）+ 券锁定 + 座位标记"已售(待支付)"
⑤ 支付成功 → 座位"已售"确认 + 券 USED；超时/取消 → 座位释放 + 券释放 + 库存回补
```

**迭代 v3（边界处理）**
| 边界 | 处理 |
|---|---|
| 同座并发 | 锁座用 Redis 原子操作（setnx/CAS），只有一人成功，其余提示"已被选" |
| 锁座超时(短5min) < 订单超时(长15min) | **锁座超时只解除"物理锁定"允许别人选；订单超时负责释放座位与券** —— 两者配合，避免用户锁了座却一直不付占用资源 |
| 锁座后未下单 | 锁座 TTL 到期自动释放 |
| 席位与票档 | 座位属于票档，扣票档库存与占座同时进行 |

**收敛设计点**
- 选座时序：加载 → 锁座(CAS+TTL) → 选券 → 下单 → 支付。
- **锁座超时(短) 与 订单超时(长) 分离**，各司其职。
- 超时走三释放（S9）。

### 🅢9 订单状态机全生命周期（核心）

**状态定义**
```
待支付(PENDING_PAY) → 已支付(PAID) → 已完成(COMPLETED)
       ↓                    ↓
   已取消(CANCELLED)      已退款(REFUNDED)
```

**事件驱动状态迁移表**
| 当前态 | 事件 | 下一态 | 附带动作 |
|---|---|---|---|
| — | 创建订单 | 待支付 | 锁库存/锁座/锁券 |
| 待支付 | 支付成功 | 已支付 | 券USED；座位确认；发电子票 |
| 待支付 | 超时(15min) | 已取消 | **库存回补 + 座位释放 + 券释放** |
| 待支付 | 用户取消 | 已取消 | 同上三释放 |
| 已支付 | 用户退款 | 已退款 | 库存回补 + 座位释放 + 券作废/退回（按规则） |
| 已支付 | 演出核销/结束 | 已完成 | — |

**超时"三释放"（核心机制）**
| 释放对象 | 怎么释放 | 幂等保证 |
|---|---|---|
| 票档库存 | Redis 库存 +1（回补） | 按 order_id 幂等，不重复回补 |
| 座位 | status 置可售 + 清 lock_token | 同上 |
| 优惠券 | user_coupon: LOCKED→UNUSED | 同上 |

**怎么触发超时（技术方案）**
- 方案：**延迟消息 / 定时扫单**。
  - `[TBD-定稿]` 本项目倾向：**定时任务扫"待支付且已超时"的订单**（简单、可靠、2C4G 友好），批量处理 + 幂等。
- 幂等：取消动作按 `order_id` 幂等（订单状态置已取消后，重复触发不再释放）。

**收敛设计点**
- 五状态 + 事件驱动迁移表。
- 超时三释放（库存/座位/券），全部按 order_id 幂等。
- 触发用定时扫单（简单可靠）。

### 🅢10 管理端运营闭环

**正常流程**
```
管理端 → 订单管理(查询/筛选/详情/退款审核) 
       → 券管理(模板CRUD/上下架/查看领取与使用)
       → 库存管理(查看/调整/审计)
       → 数据看板(销量/售罄/券核销率)
```

**发现问题**
| 问题 | 现象 |
|---|---|
| P1 重复实现 | 管理端与用户端各写一套 → 代码重复 |
| P2 权限 | 管理端需要角色/权限 |
| P3 数据一致性 | 管理端改库存/券，要和 Redis 同步 |

**迭代 v2**
- **管理端与用户端共用 service 层**（同一套业务逻辑，仅入口/权限不同），避免重复。
- 权限：管理端简单角色（admin/运营）——简化，`[TBD]` 是否做角色。

**迭代 v3**
| 优化 | 做法 |
|---|---|
| 写操作同步缓存 | 管理端改库存/券 → 同步刷新 Redis 并记审计 |
| 看板 | 聚合查询（可选缓存），展示销量/售罄/券核销率 |
| 退款审核 | 管理端审核 → 触发状态机"已支付→已退款" |

**收敛设计点**
- 管理端复用 service 层；B端不画页面仅 API（如需可加简单页面）。
- 写操作同步缓存 + 审计。

## 六、阶段A：前后端联合推演（端到端旅程 E1–E11）

> 每条 = 前端交互 + 接口 + 后端处理 + 数据/状态 + 反馈，标注"问题→优化"。

### E1 注册/登录
- FE：登录页双Tab（密码/验证码）；图形验证码图片可刷新；短信按钮60s倒计时；错误Toast。
- API：`GET /captcha`→`POST /sms/send`→`POST /user/login`。
- BE：验证码 Redis 一次性；SmsService Mock；签发双Token。
- 反馈：登录成功存 Token（Pinia+localStorage）→ 跳首页。
- 收敛：图形码前置 + 倒计时防连点 + 401 自动刷新。

### E2 浏览/搜索/详情
- FE：首页搜索框+分类Tab+演出卡片（缩略图）+分页/骨架屏；详情页海报(展示图)+场次+票档。
- API：`GET /product/list`→`GET /product/{id}`→`GET /product/{id}/sessions`→`GET /session/{id}/tiers`。
- BE：列表查询/筛选；图片多规格返回。
- 收敛：缩略图列表 + 搜索/筛选 + 场次票档联动。

### E3 预约提醒 & 开票倒计时
- FE：未开票显示倒计时（**服务端时间校准**）+ 预约按钮。
- API：`POST /reminder`（订阅）`GET /product/{id}`（返回 sale_start_time）。
- BE：场次状态机 + 预约记录 + 定时触发通知。
- 收敛：倒计时服务端校准；预约仅在"待开票"可点。

### E4 秒杀抢票（选券→下单→支付→超时）
- FE：开票倒计时；抢票按钮防重+Loading；高峰期"排队中"；抢中→选券弹层→下单；结果通过 **WS 推送（主）/轮询（兜底）**；支付倒计时。
- API：`POST /seckill/{s}/{t}`、`POST /coupon/available`、`GET /order/{id}`、`POST /payment/pay`、WS `/ws`（订阅 `/user/queue/notify`）。
- BE：Redis Lua 扣库存+一人一单 → 本地消息表 → Kafka → 消费者幂等落单 → WS 推结果；超时三释放。
- 问题→优化：抢票重复点击（前端禁用+后端幂等）；结果非即时（WS 推送+轮询兜底）；未支付占坑（超时释放）。
- 收敛：**WS主+轮询兜底** + 选券抵扣 + 三释放。

### E5 选座购票
- FE：座位图 SVG 坐标渲染+图例；点选调锁座；冲突提示"已被选"；锁座倒计时；底部已选+选券+结算。
- API：`GET /session/{id}/seats`、`POST /seat/lock`、`POST /coupon/available`、下单。
- BE：Redis CAS 锁座+TTL；座位标记；下单锁券。
- 问题→优化：同座并发（CAS 原子，只有一人成功）；锁座超时 vs 订单超时分离。
- 收敛：坐标渲染 + 锁座冲突提示 + 锁座倒计时。

### E6 购物车结算
- FE：购物车勾选/增减/删除；失效项标灰；结算。
- API：`GET /cart`、`POST /cart/add`、`POST /cart/checkout`。
- BE：购物车 CRUD；结算生成订单。
- 收敛：仅非秒杀场次；失效项不可结算。

### E7 订单管理
- FE：订单列表状态Tab+分页；详情支付倒计时+电子票+退款；待支付可取消。
- API：`GET /order/list`、`GET /order/{id}`、`POST /order/{id}/cancel`、`POST /order/{id}/refund`。
- BE：状态机 + 超时扫单 + 三释放。
- 收敛：状态Tab + 倒计时 + 电子票 + 明细（含券抵扣）。

### E8 券中心 / 我的券包
- FE：券卡片(图片/门槛/优惠/有效期)；限量券"领取"、购买券"购买"；已领置灰；券包状态Tab。
- API：`GET /coupon/templates`、`POST /coupon/receive/{id}`、`POST /coupon/buy`、`GET /coupon/my`。
- BE：通用领取引擎（限量）/券订单（购买）/策略模式。
- 收敛：领取/购买分流 + 状态置灰 + 券包Tab。

### E9 个人中心
- FE：头像上传（ImageUpload 组件）、昵称编辑、改密码弹窗。
- API：`POST /file/upload`(avatar)、`PUT /user/profile`、`PUT /user/avatar`、`PUT /user/password`。
- BE：file 管道 + 用户信息更新 + 密码重哈希。
- 收敛：头像复用图片管道；改密码不强制下线。

### E10 管理端上架/运营
- FE：本期 API（可选简单页面）。
- API：管理端接口（演出/券/库存/订单/看板）。
- BE：复用 service 层；写操作同步缓存+审计。
- 收敛：管理端复用 service；B端仅 API。

### E11 图片上传（贯穿）
- FE：ImageUpload 组件（选图→上传→回显 URL）；列表用 thumb、详情用 display。
- API：`POST /file/upload`(biz_type)。
- BE：校验→多规格压缩→MinIO→URL；异步压缩；孤儿清理。
- 收敛：统一图片管道（poster/avatar/seat_map/coupon）。
