## 版本 A：粘贴用（5 条亮点）

**TicketGo · 演出票务高并发抢票平台（个人项目）** 　2026.06 – 至今

- **秒杀一致性**：将"库存扣减 + 一人一单"封进 **Redis Lua 脚本**原子执行，杜绝超卖；抢中后经**本地消息表 + Kafka** 异步落单、消费者按订单唯一键幂等去重，保证**零超卖、零重单**。
- **通用领取引擎（抽象复用）**：发现票的秒杀与券的领取在**限量 + 限购 + 并发 + 幂等**上同构，抽出一层公共领取引擎复用，消除两份一致性代码、降低出 bug 风险。
- **订单状态机 + 超时三释放**：设计五态订单状态机，用**定时扫单 + order_id 幂等**实现超时"三释放"（库存回补 / 座位释放 / 优惠券释放），杜绝未支付占坑与重复释放。
- **选座并发一致性**：座位以 **Redis CAS + TTL** 原子锁座，与订单超时分离，超时自动释放，保证并发下同一座位不会卖给两人。
- **高并发读写稳定性**：读侧用**布隆过滤器 + 逻辑过期 + 随机 TTL** 解决缓存穿透/击穿/雪崩；写侧用 **Redis ZSet 滑动窗口 + `@RateLimit` AOP** 做用户级无侵入限流。

## 亮点问答（面试官视角 · 每条 1 个追问）

**亮点1 · 秒杀一致性**
- 问：为什么用 Lua 不用分布式锁？扣了库存但订单没建成怎么办？
- 答：Redis 单线程，脚本内一次完成"校验→扣减→去重"，天然原子、一次 RTT，比锁更快；可靠性靠**本地消息表**（业务与消息同库事务，消息必达）+ **消费者唯一键幂等**（防重）+ **超时扫单**（防丢）三段兜底。

**亮点2 · 通用领取引擎**
- 问：为什么想到抽公共引擎？
- 答：票的秒杀和券的领取都是"限量 + 限购 + 并发 + 幂等"，本质同构；抽一层复用后只有**一份一致性逻辑**，避免两处各写各的出 bug——是"识别共性、消除重复"的设计。

**亮点3 · 订单状态机 + 超时三释放**
- 问：超时怎么触发？重复触发会不会重复释放？
- 答：**定时扫"待支付且已超时"的订单**；释放动作全部按 `order_id` 幂等（订单先置"已取消"再释放），重复触发不会重复回补库存/座位/券。

**亮点4 · 选座并发一致性**
- 问：怎么保证同一座位不被卖两次？
- 答：用 **Redis `SET NX`（CAS）+ TTL** 抢锁，只有一人能占到；锁带超时自动释放；锁座超时（短）与订单超时（长）分离，各管一段。

**亮点5 · 高并发读写稳定性**
- 问：缓存穿透/击穿/雪崩分别怎么解？限流为什么用 ZSet？
- 答：穿透→布隆过滤器 + 缓存空对象；击穿→逻辑过期 + 双重检查 + Redisson 锁异步重建；雪崩→随机 TTL。限流用 **ZSet 存时间戳做滑动窗口**（精度高于固定窗口），Lua 原子执行"清过期→计数→写入"，配注解 + AOP 无侵入。

## 写法建议

1. **一条一行**，行首动词（将/设计/抽象/用），加粗核心名词即可，别写"精通/深入"。
2. **只写能讲透的**：Lua 秒杀、本地消息表、状态机、CAS 锁、缓存三件套、滑动窗口——每条都能被追问到底。
3. **数字诚实**：不写"QPS 提升 X 倍"，写"零超卖 / 零重单 / 超时自动释放"这类可验证结论；压测数据将来有再补。
4. 与 OpsMind 分工：本项目主打**高并发与一致性**，OpsMind 主打 **AI 应用工程化**，别互相抢戏。
