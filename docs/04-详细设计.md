## T1 秒杀抢票链路

### 难点
开票瞬间万级并发抢同一票档：传统"查 DB 再扣减"会**超卖**，且瞬时写会把 MySQL 打爆。

### 设计（三段式）
```
① 裁决：Redis Lua 原子扣库存（防超卖）
② 削峰：本地消息表 → Kafka → 消费者异步落单（防打爆 DB）
③ 兜底：消费者幂等 + 超时对账（防重单/丢单）
```

### ① Redis Lua 扣库存（伪码）
```lua
-- KEYS[1]=stock:{tierId}   KEYS[2]=seckill:users:{tierId}   ARGV[1]=userId
if redis.call('exists', KEYS[1]) == 0 then return -1 end   -- 未预热
local stock = tonumber(redis.call('get', KEYS[1]))
if stock <= 0 then return 0 end                             -- 售罄
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return -2 end  -- 一人一单
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return 1                                                    -- 成功
```
- **为什么用 Lua**：Redis 单线程执行脚本 → 校验+扣减+去重一次原子完成，无竞态。
- **返回码**：1 成功 / 0 售罄 / -1 未预热 / -2 重复。

### ② 落单（本地消息表 + Kafka）
```
抢票成功 → 同一 DB 事务写：order(待支付) + message_outbox(待发送)
        → 定时 job 投递 message_outbox → Kafka topic=order-created
        → order-service 消费者落库（幂等）
```
- **为什么本地消息表**：业务与消息同库事务 → 只要事务提交，消息必然进待发表，job 迟早投出 → **不丢**。
- **为什么不用 Kafka 事务消息**：本地消息表更简单、可控，单机友好（Kafka 事务消息作为对比/演进点）。

### ③ 幂等与兜底
- 消费者按 `order_no` / `biz_key` 唯一索引幂等 → 重复消息只落一次。
- 超时扫单 → 未支付取消 → 三释放（T7）。

### 边界
| 边界 | 处理 |
|---|---|
| 库存未预热 | Lua 返回 -1，接口提示"未开票/系统繁忙" |
| 重复抢 | -2，提示"您已抢过" |
| 扣减成功但落单失败 | 消息在 outbox，job 重试；极端失败进死信 |
| 大量失败 | 有限重试 + 死信队列 |

### 面试话术
*"库存裁决放 Redis 用 Lua 保证原子（零超卖）；扣中走本地消息表+Kafka 异步落单削峰（保护 DB）；消费者唯一键幂等防重单、超时对账防丢单。"*

## T2 削峰三层防线

### 难点
瞬时流量远超系统处理能力，若不拦截会把 Redis/DB/服务全打挂。

### 设计（由外到内三层）
| 层 | 手段 | 作用 |
|---|---|---|
| ① 网关限流 | Gateway + **Sentinel** 全局/热点限流 | 挡住超额流量，返回"活动火爆" |
| ② 用户级限流 | **Redis ZSet 滑动窗口 + Lua** + `@RateLimit` AOP | 防单用户刷（如 1 秒 1 次抢票） |
| ③ 异步削峰 | 本地消息表 + **Kafka** | 把"瞬时洪峰"摊平成"稳态消费" |

### 用户级滑动窗口（Lua 伪码）
```lua
-- KEYS[1]=rate:{userId}:{api}  ARGV: now, windowMs, limit
redis.call('zremrangebyscore', KEYS[1], 0, ARGV[1]-ARGV[2])
local n = redis.call('zcard', KEYS[1])
if n >= tonumber(ARGV[3]) then return 0 end
redis.call('zadd', KEYS[1], ARGV[1], ARGV[1])
redis.call('pexpire', KEYS[1], ARGV[2])
return 1
```
- `@RateLimit(key, window, limit)` + AOP 切面：无侵入，方法级生效。

### 效果/话术
*"网关挡全局、Redis 滑动窗口挡用户级、Kafka 摊平洪峰，三层各司其职；DB 稳态承压（设计目标 300~500 单/s）。"*

## T3 选座锁定与释放

### 难点
并发下同一座位不能被卖给两人；用户"锁了不买"要能自动释放。

### 设计
- 座位状态：`0 可售 / 1 锁定 / 2 已售`。
- **锁座**：Redis `SET seat:lock:{sessionId}:{seatId} {token} NX PX 300000`（CAS + 5 分钟 TTL）。
  - NX 保证只有一个请求抢到；token 用于"释放时校验归属"。
- **释放**：TTL 到期自动可抢；或主动 `DEL`（校验 token）。
- **下单**：锁座成功后下单，座位置"已售(待支付)"。
- **两个超时分离**：
  - **锁座超时（短，5min）**：只解除物理锁定，允许别人选。
  - **订单超时（长，15min）**：负责释放座位 + 券 + 库存。

### 边界
| 边界 | 处理 |
|---|---|
| 同一座位并发点击 | NX 只有一个成功，其余提示"已被选" |
| 释放非本人锁 | 校验 token 归属 |
| 锁座后未下单 | TTL 到期自动释放 |
| 支付成功 | 座位转"已售"并清锁 |

### 话术
*"锁座用 Redis SET NX 原子占座 + TTL，超时自动释放；锁座超时（短）与订单超时（长）分离，各司其职。"*

## T5 Redis 缓存全景

### 难点（三座大山）
| 问题 | 现象 | 解决 |
|---|---|---|
| **缓存穿透** | 查不存在的数据，每次都打到 DB | **布隆过滤器**拦截 + **缓存空对象**（短 TTL）双保险 |
| **缓存击穿** | 热点 key 过期瞬间，大量请求同时打 DB | **逻辑过期 + 双重检查 + Redisson 分布式锁**，加锁线程异步重建缓存 |
| **缓存雪崩** | 大量 key 同一时间过期 | **随机 TTL**（基础 TTL + 随机偏移）+ 多级缓存（可选 Caffeine L1） |

### 逻辑过期重建流程
```
读缓存 → 未过期直接返回；已过期 → 尝试获取分布式锁
  → 拿到锁：二次检查（双重检查）→ 仍是过期 → 开异步线程重建 → 返回旧数据
  → 未拿到锁：直接返回旧数据
```

### 话术
*"穿透用布隆+空对象双保险；击穿用逻辑过期+双重检查+分布式锁异步重建；雪崩用随机 TTL；热点更新时删除缓存而非更新。"*

## T6 Kafka 消息设计

### Topic / 分区
| Topic | 用途 | 分区键 | 消费者 |
|---|---|---|---|
| `order-created` | 秒杀落单 | `order_no`（保证同单有序） | order-service |
| （可选）`order-notify` | 结果通知 | `user_id` | notification/ws |

### 不丢失三环节
| 环节 | 措施 |
|---|---|
| 生产者 | `acks=all` + 重试 + 幂等生产者 |
| Broker | 持久化（落盘）+ 多副本（演进点） |
| 消费者 | **手动提交 offset**（处理完才提交） |

### 不重复
- 消费者幂等：`order_no` 唯一索引，重复插入命中唯一键即跳过。

### 不堆积
- 分区数预留（并行度）；消费端批量处理；**死信队列**兜底失败消息。

### 顺序
- 同一订单的消息发往同一分区（按 `order_no` hash）→ 分区内有序。

### 失败处理
- 有限重试（指数退避）→ 死信队列 → 人工/补偿重投。

### 话术
*"三环节堵不丢：acks=all、持久化多副本、手动提交；消费者唯一键幂等防重；分区预留+批量+死信防堆积；按订单号分区保单有序。"*

## T7 订单状态机与超时取消

### 状态机
```
待支付(PENDING_PAY) → 已支付(PAID) → 已完成(COMPLETED)
       ↓                    ↓
   已取消(CANCELLED)      已退款(REFUNDED)
```

### 迁移表
| 当前态 | 事件 | 下一态 | 动作 |
|---|---|---|---|
| — | 创建 | 待支付 | 锁库存/锁座/锁券 |
| 待支付 | 支付成功 | 已支付 | 券USED、座位已售、发电子票 |
| 待支付 | 超时/取消 | 已取消 | **三释放** |
| 已支付 | 退款 | 已退款 | 库存回补 + 座位释放 + 券处置 |
| 已支付 | 演出结束/核销 | 已完成 | — |

### 超时三释放（按 order_id 幂等）
| 对象 | 释放 |
|---|---|
| 票档库存 | Redis 库存 +N |
| 座位 | status 置可售 + 清 lock_token |
| 优惠券 | LOCKED → UNUSED |

### 触发方式
- **定时扫单**：扫描 `status=待支付 AND pay_expire_at < now` → 取消并三释放。
- **幂等**：订单先置"已取消"，重复触发不再释放。

### 话术
*"五态订单状态机 + 事件驱动；超时由定时扫单触发，按 order_id 幂等做库存/座位/券三释放，杜绝占坑与重复释放。"*

## T8 支付回调与对账 / Seata 边界

### 设计
- 支付走 `payment-service`（Mock），回调 `POST /payment/callback`。
- **回调幂等**：按 `order_no` 唯一/状态判断，重复回调只处理一次。
- **对账**：定时比对"支付成功但订单未更新"的差异，补偿。

### Seata 边界（核心取舍）
| 场景 | 方案 | 理由 |
|---|---|---|
| 抢票链路（扣库存→落单） | **Kafka 最终一致** | 高并发下强事务代价太大 |
| 支付/退款（订单↔支付） | **Seata AT**（局部） | 资金相关，需强一致 |

### 话术
*"抢票链路用最终一致（本地消息表+幂等），因为高并发下跨服务强事务代价太高；支付/退款这类资金场景才上 Seata AT 保证强一致。"*

## T9 数据库索引与表设计

### 关键表索引（每条附理由）
| 表 | 索引 | 服务的 SQL / 为什么 |
|---|---|---|
| `user` | `uk_phone(phone)` | 登录按手机号查；唯一防重复注册 |
| `product` | `idx_cat_status(category,status)` | 首页按分类+状态筛选 |
| `product` | `idx_status_time(status, create_time DESC)` | 列表按上架时间倒序 |
| `session` | `idx_prod_time(product_id, show_time)` | 详情页查某演出的场次 |
| `session` | `idx_sale(sale_start_time, sale_end_time, status)` | 定时任务扫待开票/已结束 |
| `ticket_tier` | `idx_session_price(session_id, price)` | 场次下按价格列票档 |
| `seat` | `idx_session_tier_status(session_id, tier_id, status)` | 座位图按场次+票档查可用座 |
| `seat` | `idx_lock_expire(lock_expire_at)` | 扫超时锁座释放 |
| `order` | `uk_order_no(order_no)` | 幂等 + 单查 |
| `order` | `idx_user_status_time(user_id, status, create_time DESC)` | "我的订单"按状态倒序 |
| `order` | `idx_status_expire(status, pay_expire_at)` | 扫超时订单 |
| `message_outbox` | `idx_status_retry(status, next_retry_at)` | 扫待投递/重试消息 |
| `message_outbox` | `uk_biz_key(biz_key)` | 幂等 |
| `user_coupon` | `idx_user_status(user_id, status)` | 我的券包按状态 |
| `coupon_template` | `idx_status_time(status, create_time DESC)` | 券中心列表 |

### 设计原则
- 唯一索引承担**幂等**职责（order_no / biz_key / phone）。
- 联合索引顺序：**等值列在前、范围/排序列在后**（最左前缀）。
- 高频列表查询走**覆盖/联合索引**，减少回表。
- 分库分表：**演进点**（本期单库单表，先按分表路由约定编码）。

### 话术
*"每个索引都对应一条真实 SQL：比如 order 的 (user_id,status,create_time) 服务'我的订单按状态倒序'；唯一索引还兼职幂等；分库分表作为演进。"*

## T10 微服务 / 分布式ID / 网关

### 微服务
- 见 02-概要设计（gateway/user/product/seat/seckill/order/cart/coupon/payment/notification + common）。
- 服务**无状态**（JWT 无状态 + Redis 存会话）→ 可水平扩展。

### 分布式ID
- **雪花算法**：`timestamp(41) + 机器ID(10) + 序列(12)`，全局唯一、趋势递增。
- 用于 order_no（另可加业务前缀/时间）。

### 网关
- 路由转发、统一鉴权（校验 JWT）、全局限流、跨域、日志/traceId。
- **加新服务 = 加一条 Nacos 注册 + 网关路由**（可扩展）。

### 话术
*"服务无状态可水平扩；ID 用雪花保证跨库全局唯一；网关统一鉴权/限流/路由，加服务只改配置。"*

## T11 优惠券机制（策略模式 + 通用领取引擎）

### 策略模式
```java
public interface CouponStrategy {
    String type();
    boolean applicable(OrderContext ctx, UserCoupon coupon); // 门槛/范围校验
    BigDecimal calculate(BigDecimal origin, UserCoupon coupon); // 折后价
}
// 实现：FullReduceStrategy / DiscountStrategy / ImmediateStrategy
// 工厂：Map<String, CouponStrategy>（Spring 注入 List 后建 map）
```

### 通用领取引擎（票/券复用）
```
票秒杀：Lua 扣票档库存 + 一人一单
券领取：Lua 扣券库存 + 每用户已领数 < per_user_limit
→ 同一套：原子扣减 + 用户去重 + 幂等 + 异步落单
```

### 券生命周期
```
未用 → (下单)锁定 → (支付)已用
        └(取消/超时)释放 → 未用
        └(过期)已过期
```

### 购买券（不限量）
- `order_type=COUPON`；校验"已购+本次 ≤ per_user_limit"；支付成功发券（幂等）。

### 话术
*"券种用策略模式（开闭原则）；票/券在限量+限购+并发+幂等上同构，抽通用领取引擎复用；券与订单'锁定→使用/释放'联动防重复使用。"*

## T12 图片处理机制（MinIO + 多规格压缩）

### 流程
```
上传 → 校验(格式 jpg/png/webp + 大小上限) → 压缩(等比缩放 + 质量压缩)
     → 生成 原图/展示图/缩略图 → 存 MinIO → 返回三 URL
```
- 列表用 `thumb_url`、详情用 `display_url`。
- 大图**异步压缩**（线程池/@Async），压缩完回填 URL。
- 压缩参数（最大宽、质量）放 Nacos。
- 未绑定业务的图（`is_orphan=1`）定时清理。

### 实现选型
- 压缩：**Thumbnailator**（简单）或 ImageIO。
- 存储：MinIO Java SDK，bucket 分目录（poster/avatar/seat_map/coupon）。

### 话术
*"多规格压缩（原图/展示/缩略）+ 异步压缩，列表走缩略图省带宽；MinIO 对象存储；孤儿图定时清理。"*

## T13 WebSocket 实时推送

### 定位
秒杀/订单结果**即时推送**；断线时**降级轮询**兜底。

### 设计
- 选型：**Spring Boot WebSocket + STOMP + SockJS**。
- **握手鉴权**：WS 无法带自定义 Header → 用 query/子协议传 Token，握手拦截器校验。
- **连接管理**：`userId → WebSocketSession` 映射（单机内存 Map）。
- **订阅**：`/user/queue/notify`。
- **心跳/重连**：定时 ping/pong；前端断线重连。
- **消息类型**：`{type: SECKILL_RESULT|ORDER_STATUS, data}`。
- **多实例**：Redis Pub/Sub 广播（演进点）。

### 兜底
- WS 不可用/未连上 → 前端轮询 `GET /order/{id}`。

### 话术
*"秒杀结果用 WebSocket 实时推送（握手用 query 传 Token，内存维护 userId→Session），断线降级轮询兜底；多实例用 Redis 广播作为演进。"*
