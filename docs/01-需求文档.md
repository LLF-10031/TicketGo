## 一、产品定位

**一句话**：面向普通观众的**在线演出/赛事票务抢票平台**（类大麦/猫眼）。观众浏览→开票瞬间抢票（或选座）→支付拿电子票；主办方上架演出、配票价、看卖座（B端仅 API + 数据模型，不画页面）。

**与同类区别**：核心深挖"抢票一致性与高并发"（零超卖、零重单、削峰），而非铺功能广度。

### 3.3 不做/演进点

| 功能 | 决定 | 理由 |
|---|---|---|
| 广告系统 | ❌不做 | 独立高并发领域，演进路线提一句即可 |
| 会员/评价 | 🔸演进点 | 文档化不实现，步骤写清建库→注册→配路由→依赖 |
| 电子票核销 | ❌砍/扩展点 | 需检票端子系统，demo 价值低 |
| 发票 | ❌砍 | 与平台价值无关 |
| 实名/常用购票人 | ❌砍/扩展点 | 防黄牛用轻手段 |
| Redis 集群/分库分表 | 🔸不实现 | 降复杂度；只写演进路线 + 面试问答 |

## 四、用户角色与核心流程

### 4.1 角色

- **普通用户（观众）**：浏览→抢票/选座→支付→电子票
- **主办方/运营**：上架演出→配置场次/票档/座位图→设置开票时间与库存→查看销售

### 4.2 核心流程（C端）

```
注册/登录 → 首页浏览/搜索 → 演出详情（看票价/座位图）
  → 两种购票路径：
    A. 免选座秒杀：开票时间到 → 抢票（Redis Lua 扣库存）→ 落单（Kafka 削峰）
    B. 选座购票：座位图选座 → 加入购物车（非秒杀）/ 直接下单（秒杀）→ 支付
  → 支付（限时15分钟，超时自动取消，回补库存）
  → 订单列表 / 电子票
  → 我的界面（可查订单、退款、收藏、提醒管理）
```

## 五、非功能需求（设计目标，待压测验证）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 开票峰值 | ≥2000 QPS（Nginx/Gateway/Redis侧） | 2C4G 单机 JMeter 实测可达区间 |
| 稳态下单 | 300~500 单/s | 尊重数据库写入上限 |
| 正确性 | 零超卖 · 零重单 | 项目灵魂，与机器大小无关 |
| 抢票接口 P95 | <500ms | Redis+Lua 短路径 |
| 可用性 | 99.9%（单机尽力） | — |
| 扩容 | 加节点即可线性扩展 | 架构预留，先本地后上云 |

### 可扩展性底座（P0 架构原则）

从第一天按集群语义写，六项落点：

| 扩展点 | 设计手段 |
|---|---|
| 加实例 | 服务无状态 + JWT 无状态 + Redisson 中心化锁 |
| Redis 集群 | 库存分桶 + Lettuce（天然 Cluster） |
| Kafka 扩展 | 分区预留 + 按订单号 hash 分区 |
| 数据库集群 | 按领域垂直分库 + 订单按 user_id 分表 + 读写分离预留 |
| 配置中心 | Nacos 动态配置，改配置不重启 |
| 分布式ID | 雪花 ID 全局唯一 |

| 范围内 | 说明 |
